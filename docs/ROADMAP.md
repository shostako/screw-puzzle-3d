# ロードマップ

仕様は [SPEC.md](SPEC.md)、技術や見た目の判断は [DECISIONS.md](DECISIONS.md)。

進め方: 1スレッドで1項目を進める。仕上げの段階（E）の順番は「E 仕上げ」の「進め方」に書いた。終わったら（PR の ci が成功して master にマージしたら）チェックを付け、その項目の「分かったこと」を書き足す。上から順に進め、前の項目が master に入るまで次を始めない。

どの項目でも守ること:

- ゲームのルール（ねじが外せるか、箱とスロットの動き、クリアと詰み、盤面が解けること）はテストで守る。テストは `npm test` から走り、CI（`scripts/ci.sh`）が毎回回す。
- 画面が変わる PR には、ヘッドレスのブラウザで撮ったスマホ縦画面のスクリーンショットを付ける。
- 外部の読み込み（CDN など）はしない。ライブラリは npm で入れてビルドに同梱する（Android アプリで、ネットが無くても動くように）。

## M2 ルールの核: 描画なしで1局を最後まで進められる

- [x] 完了

やること

- ゲームの状態とルールを、描画にも物理にも依存しない純粋なモジュールにする。2D 版の `index.html` と README の「現在のルール」が正本。
  - 色つきの箱が2つ。ねじは同じ色で空きのある箱へ（同じ色が2つなら多く入っている方）。3本で満杯になると消え、次の箱が出る。
  - 合う箱が無いねじは待機スロット（5個）へ。新しい箱が出たら、スロットの同じ色のねじが自動で移る。
  - 全部の箱を埋めたらクリア。スロットが満杯で入れられるねじが無ければ詰み。
  - 板のねじが2本以上なら固定、1本ならぶら下がり、0本なら落下、という板の状態の移り変わり。
- 「ねじが外せるか」は、外から渡す判定（隠れているか）を受け取る形にしておく。3D の幾何は M3 で入れる。

完了条件

- 上のルールそれぞれにテストがあり、CI で通る。
- 手で書いた小さな盤面（板とねじの一覧と箱の順番）を、テストの中でクリアまで、また詰みまで進められる。

## D 見た目を本格化する（2026-10-03 に決めた方針）

見本は [docs/design/](design/)。`mockup.src.html` は提案ページの元（three.js の試作。`__LEVELS__` に盤面の JSON を入れると開ける）で、ねじとネジまるの形・寸法・動きはここから写してよい。上から順に1スレッド1項目で進める。

決まったこと

- 雰囲気は「おもちゃブロック調」。淡い色の艶のある板（角を丸める）、空色のグラデーションと白い丸いマット。
- ねじは六角穴付きボルト（キャップボルト）風。色はカラフルなアルマイト調。頭の径 ≈ ねじ径の 1.5 倍、頭の高さ ≈ ねじ径（JIS B 1176 に寄せる）、側面に縦のローレット、上の角は面取り、暗い六角穴。当たり判定の半径は今のまま変えない。
- マスコットは「ネジまる」。金色のキャップボルトの頭が顔、銀のねじ部が胴、白いソフビの腕と手袋、銀の脚、青い靴、六角レンチ。待機・成功（^ ^ の目でバンザイ回転ジャンプ）・失敗（× の目と汗でうなだれる）。見本の絵は `docs/design/nejimaru_*.png`（ユーザーの PC の Codex で生成）、立体は `nejimaru-3d-idle.png`。

## E 仕上げ（2026-10-03 棚卸し。製品版に迫る出来へ）

M・D・後回しの項目で遊びはそろい、実機でも動いた。ここからは新しい機能を足すより、いまある遊びを一段上げる。雰囲気（おもちゃブロック調、キャップボルト風のねじ、ネジまる）は決定済みで変えない。

棚卸しは、ビルドした `dist/` をヘッドレスの Chromium で 390×844（DPR 2）に開いて見た。撮ったものは [docs/screenshots/e0-audit/](screenshots/e0-audit/)（ステージ 1・8・14・20・37、ステージ 8 の途中とクリア、遊び方、設定）。

### 見えた差（製品版と比べて）

画面と見た目

- 構図: 待機スロットの下の案内の行から立体の上端まで、縦に 170px ほど空いている。立体は画面幅の 7 割弱で、下半分のマットの上に小さく浮いて見える。カメラの距離は `START_DISTANCE` の固定で、盤面の大きさ（箱・車・家）に合わせていない。
- 手触り: 指を離すと回転がその場で止まる（慣性が無い）。製品のパズルは惰性で少し回って止まる。
- 質感: 板の色が淡く、ステージ 1 の白い天板は白いマットに溶ける。板が重なった所や接する所の暗さが無いので、組んだ物というより面の寄せ集めに見える。背景はどのステージも同じ空色。
- 色の見分け: ねじは色だけで区別している。赤・ピンク・オレンジ、青・水色・ティールが近く、6 色のステージや色覚の違う人には見分けにくい。
- 起動: 読み込み画面もタイトルも無く、いきなりステージが出る。Android のアイコンとスプラッシュは Capacitor の既定のまま。文字は丸ゴシック指定だが、Android には入っていないので端末の既定の角ゴシック（Noto Sans CJK など）で出る。
- クリアのカード: 跳ねるネジまるがカードの上へはみ出して、後ろの案内の文字に重なる。★3 でも ★1 でも喜び方が同じ。

遊びとステージ

- 形の種類が少ない: 家具 3（箱・本棚・机）と題材 3（車・家・ぶた）の 6 種を、ステージ 7 から 6 周期で回している。8・14・20・26… はいつも車で、色が違うだけに見える。ステージ 37 の箱はステージ 1 の箱とほとんど同じ見た目。
- 難しさの曲線が早く平らになる: ねじの本数は 16 前後で頭打ち（24 本）、色は 23 から 6 色で止まる。進んでも「同じ形で色が多いだけ」になり、山と谷（易しい息抜きと章の終わりの大物）が無い。
- 導入: 最初の案内は「1本指で回す・ねじをタップで外す」の1行だけで、ずっと出たまま。札の下のねじ（2〜3）、中の板（4）、待機スロット、親子の決まり（子が残ると親の最後のねじが外せない）を、出てきた時に教えていない。
- 報酬: クリアで ★ と時間は出るが、それまでのステージの星を見返す所が無く、先に何があるか（新しい題材）も見えない。
- 続き: 再読み込みやアプリの切り替えで、遊んでいる途中の局面が消えて、そのステージの最初から（おまかせ・今日の1問はステージへ）戻る。Android は裏に回したアプリを OS が落とすので、製品では途中の保存が要る。
- 音: 効果音は Web Audio の合成のピコ音で、ねじの金属感や箱が閉まる手応えが弱い。BGM は無い。

### 進め方

- 1スレッドで1項目。項目の中の細かい選び方はスレッドが決め、DECISIONS.md に1〜2行残す。実機でないと分からない点は [DEVICE-CHECK.md](DEVICE-CHECK.md) に1行ずつ足して先へ進む。
- 見た目を変える PR は、390×844 の「変更前」と「変更後」を並べたスクリーンショットを付ける（`scripts/screenshot.mjs` に組を足す）。
- 並べて走らせてよい。ただし `src/main.js`・`src/style.css`・`index.html`・この ROADMAP は多くの項目が触るので、PR の前に master を取り込んで競合を解消する。下の「順番」にある項目は、前の項目が master に入ってから始める。
- 上から順に、遊び始めの印象を決めるものを先に置いた。

### E2 質感と光

- [x] 完了

- 板の色の並び（`THEME`）を見直し、白い板がマットに溶けない明るさと、題材らしい色（車はボディ色、家は壁と屋根、ぶたはピンク）にそろえる。板の縁に細い明るい線（面取りの反射）か暗い線を入れて、輪郭を立たせる。
- 板が接する所・重なる所の暗さを出す。影の地図より安い方法（板ごとに焼いた接地の暗さ、または SSAO を画質「自動」の時だけ）から選ぶ。描く回数の約束（板1・ねじ3）と三角形 8 万枚を守る。
- 背景: 空のグラデーションを題材や章で少し変えられる形にする（色は `THEME` に）。マットの縁を柔らかく。
- 色の見分け: ねじの六角穴の周りか頭の上面に、色ごとの小さな刻印（●▲■★◆♥ など）を入れる。箱と待機スロットの印にも同じ刻印。設定に「刻印」入り切りを足すかはスレッドが決める。
- 触るファイル: `src/theme.js`、`src/scene.js`、`src/env.js`、`src/style.css`（`body` の背景と箱・スロットの印だけ）、`test/theme.test.js`
- 完了条件: ステージ 1・8・10・12・37 の変更前と後。6 色のステージで、色を抜いた（グレースケールの）スクリーンショットでもねじの色の組が区別できる。速さの検査（`test/effects.test.js` の三角形と描く回数）が通る。

分かったこと（E2 を終えて）

### M2 で分かったこと

- ルールは `src/rules.js`。盤面は `{ plates: [{ id }], screws: [{ id, plate, color }], queue: [色...] }` の形で、`newGame(level)` で始め、`removeScrew(state, id, isBlocked)` で1手進める。状態は毎回新しいオブジェクトで返り、前の状態は書き換えない（戻る・ヒントの探索でそのまま使える）。
- `removeScrew` は `events`（`toBox` / `toSlot` / `plate` / `boxFull` / `boxSpawn` / `slotToBox` を起きた順に）を返す。M4 の描画はこれを順に再生すれば、ねじが飛ぶ先・箱の入れ替わり・板の落下を追える。板の状態は `plateState(state, id)`（fixed / hanging / fallen）。
- 外せない理由は `checkRemove` が返す `gone` / `blocked` / `full`。`blocked` のときは震えて拒否、`full` のときは待機スロットを光らせる（2D 版と同じ）。
- 隠れ判定は `isBlocked(screwId, state)` を外から渡す。テストでは「このねじはこの板たちに隠れている、板が落ちれば見える」という表（`coverBlocker`）で代用している。M3 の 3D 判定も同じ形の関数にすれば、そのままルールにつながる。ぶら下がった板も隠し続ける扱いは、判定側で決める。
- 詰みは「外せるねじが1本も無い」で決めている。2D 版の「スロットが満杯で入れられるねじが無い」は、最上階層のねじが必ず見えている 2D 版ではこれと同じ。3D ではスロットに空きがあっても全部隠れていることがありうるので、一般の形にした。板が揺れている間は詰みを決めない、という時間の扱いは M5 で物理側に持たせる。
- 盤面は `validateLevel` が「色ごとのねじ = 箱の数 × 3」などを検査し、合わなければ例外にする。M6 の生成器の出力もこれを通す。
- 2D 版の飛んでいる途中・フタが閉まる途中などの時間は持たず、1手で箱の入れ替わりまで済ませる。移しただけで満杯になった箱は、その場で消えて次の箱が出る（連鎖する）。

### M3 で分かったこと

- 盤面の形は `src/board.js` の冒頭に書いた形。M2 の盤面に、板の `size`（または凸の `outline`）・`thickness`・`position`・`rotation`（Euler XYZ）か `quaternion`、ねじの `position`（頭の中心、板の表面上）・`dir`（抜ける向き）を足しただけなので、`newGame` にそのまま渡せる。板は局所の xy 平面の厚板で、法線が局所 z。

### M4 で分かったこと

- 画面のつなぎは `src/main.js`、盤面から three.js の立体を作るのは `src/scene.js` の `buildBoard(level)`（板は輪郭を押し出した Mesh、ねじは色の丸頭＋十字の溝の Group で `userData.screwId` を持つ）。1局の進行は `src/game.js` の `createGame(level)`（`tap(id)` が `reason` / `events` / `status` を返す。クリアか詰みの後は `over`）。描画に依存しないのでテストできる。

- ルールの状態はタップの瞬間に進め、演出は後から出来事の列を再生する（続けてタップすると再生を速める）。やり直しは `generation` を進めて古い演出を捨てる。

- スクリーンショットのスクリプトは、CDP のタッチでねじをタップして外れることと、隠れたねじが拒否されることを確かめ、`window.__app.legal()` で外せるねじを順に外してクリアまで進める。ページ側の目印は `window.__app`（`rendered` は演出の終わりも待つ）。

### M5 で分かったこと

- 物理は `src/physics.js`。`await initPhysics()` を1回してから `createPhysics(level)`。板は全部固定で始まり、`syncPlates(ph, state)` をルールの状態が変わるたびに呼ぶと、ねじ1本の板はぶら下がり（`hang`）、0本の板は自由になる（`release`）。始めからねじ1本の板もこれで扱える。`step()` は 1/60 秒進め、盤面の外へ落ちきった板の id を返す。板の状態は `mode(id)`（fixed / hanging / loose / gone）。
- 盤面の座標で解く。画面では毎フレーム、世界の下 (0, -1, 0) を立体の回転の逆で盤面の座標に直して `setDown` に渡す。向きが変われば止まっていた板も動き出す。
- 隠れ判定は `ph.blocker()`（今の姿勢 `ph.poses()` と、消えていない板 `ph.present()` で `sweepHits`）。止まった板・ぶら下がった板も隠す。詰みは `fixedBlocker(level)`（固定の板だけで判定、board.js）を `createGame` の3つ目の引数に渡して決める。物理なしのテストや M6 の探索は今までどおり `blockerFor` を使える。
- 固定の盤面は、外す順と向きによって「落ちた板が箱の中や縁に残って、ねじを隠し続ける」ことが普通に起きる。テスト（`test/physics.test.js` の `playBox`）とスクリーンショットのスクリプトは、外せるねじが無くなったら重力の向き（立体の向き）を6方向に順に変えて板を払い落とし、クリアまで進めている。M6 の探索で「回せば払える」を手順に入れるかは、ここを参考に決める（安全側に見積もるなら、動く板は盤面から消えるまで隠し続けるとみなす）。
- 箱の前板・横板は、ぶら下がるとすぐ底板の縁に引っかかって止まる（`test/physics.test.js` に場面がある）。ぶら下がりがよく見えるのは天板（立体を倒すと軸のまわりに振れて箱の中が見える）。
- Rapier の `body.sleep()` で眠らせた、継ぎ手つきの板を起こすと、継ぎ手が効かなくなって板が飛んでいった。落ち着いたかどうかは自分で数え（`QUIET_*`）、眠らせはしない。
- 同じ板のねじを、間を空けて1本ずつ外すと、間にぶら下がって回ってから落ちる。続けて外すとその場で落ちる。スクリーンショットの「札が天板の上で止まる」場面は、2本を同じタイミングで外している。
- 決定性は、同じシードで同じ操作をした2回の、全部の板の姿勢と落ちた順を JSON で比べて確かめている。画面ではフレームの間隔で刻みの数が変わるので、同じ指の動きでも同じにはならない（操作をした刻みの位置まで同じなら同じ）。
- スクリーンショット用に `window.__app.view(x, y, z, 距離)`（立体の向きを Euler で直接決める）と `plateModes()` を足した。`rendered` は物理が落ち着くのも待つ。
- dist の JS が約 5MB になった（Rapier の wasm を base64 で埋め込んでいるため）。M8 で、wasm を別ファイルにする版（`@dimforge/rapier3d-deterministic`）や読み込みの分け方を検討する。

### M6 で分かったこと

- 生成は `generateLevel(seed, opts)`（`src/generator.js`）。返り値は M3 の盤面の形そのもので、`meta` に `{ seed, kind, solution, tries, fallback, attempt }`。`opts` は `kind`（box / shelf / table）・`colors`（色の数、既定 4）・`labels`（札の数、既定 2）・`win` / `noise`（色の混ぜ方。大きいほど待機スロットを使う割り当て）・`budget`（探索の打ち切り）。M7 はステージ番号からこれらを決めればよい（今はシード 1〜300 で板 5〜11 枚、ねじ 12〜30 本。300 のうち 2 つは色の割り当てが最後の砦（順番どおりに箱が埋まる易しい割り当て）になった）。
- 解ける保証の隠れ判定は `safeBlocker(level)`（`src/safe.js`）。ルールの `isBlocked` の形なので `removeScrew` / `legalMoves` / `solve` にそのまま渡せる。後回しのヒントや「戻る」も、これと `solve(level, safeBlocker(level))` を途中の状態から呼ぶ形で作れる（`solve` は今は始めの局面からだけなので、状態を受け取れるように足す）。
- 探索は `solve`（`src/solve.js`）。深さ優先で1つ見つけたら終わり、行き止まりの局面は覚える。板を外し切る手（残り1本）を先に、ぶら下げる手（残り2本）を後に試すのが効いた（ぶら下がった板は届く範囲全部を隠すので、増やすと行き詰まりやすい）。局面の鍵の作り方に気をつける（'board' と 'box' の頭文字が同じで、最初は別の局面を同じとみなして解けないと答えていた）。
- 形が悪いと探索は打ち切りまで全部調べて遅くなる。板が互いのねじを隠し合う置き方（例: 上の棚板の下向きのねじと、下の棚板の上向きのねじ）は `peelable` で安く弾き、ねじだけ置き直している。
- 生成の速さ（手元の Node、シード 1〜300）: 平均 21ms、最悪 0.24 秒。スマホは数倍遅いとみて、最悪でも 1 秒程度。重いのは見積もりの抜け出す道の判定と、色の割り当てが外れたときの探索の打ち切り。テストは平均 100ms・最悪 1 秒で見張っている。
- 物理との突き合わせ（`test/safe-physics.test.js`）で、M5 の物理のバグが見つかった: 細長い板の当たりの形が実物より太り、壁の間の棚板が挟まって、どの向きに傾けても落ちなかった。`plateVertices` の縮め方を「辺ごとに同じ幅」に直した。手元で 1〜1000 のシードを再生し、見積もりが甘い場面は 0。
- 縮め方を直す前の突き合わせでは、机の天板がぶら下がったときに、軸のねじが幕板や脚にかすって隠れる場面も 2 つ（1〜200 のうち）出た。ねじのすぐ脇に別の板の縁がある置き方で、軸のわずかな傾き（ねじ1本で大きな板を支えるたわみか、太った当たりの形に押されたか）によるものと見ている（確かめてはいない）。直した後は 1000 シードで出ていないが、また出たら見積もりの円柱を少し太らせる。
- 画面は `?seed=番号&kind=種類` で生成盤面を開ける。`window.__app.solution` が見つけた手順で、スクリーンショットのスクリプトはこれを順に外し、物理で隠れていたら向きを変えて払い落としてからクリアまで進める。

### M7 で分かったこと

- ステージは `src/stages.js`。`stageConfig(n)` が生成器の設定（`generateLevel` の opts と、盤面が満たすべき条件 `want`）を返し、`stageLevel(n)` がシードを n × 1000 から順に試して条件に合う最初の盤面を返す（`meta.stage` と `meta.seed` 付き。`?seed=` で同じ盤面を開ける）。盤面は保存せず毎回作る。
- 生成器に形の指定を足した: `open`（箱の前を開けるか）・`inner`（中の仕切り・棚板を入れるか）・`maxPer`（板1枚のねじの上限）・`alternate`（箱の色を混ぜず順に回す）。どれも省略すれば M6 と同じ乱数の使い方なので、シード 1〜60 の既定の盤面は M6 と1文字も変わらない（手元で比べた）。
- 並び: 1 閉じた小さな箱（ねじ 12 本・2 色・交互の箱。出ている 2 箱がいつも違う色なので、どの順に外しても詰まない。最初の向きで見えている面を外し終えると、裏と底を回して探すことになる）、2〜3 札、4 中の板、5 本棚、6 机。7 から先は箱・本棚・机を順に回し、色 4→6、札 2→4、ねじの数の下限と色の混ぜ方（win / noise）を数ステージごとに上げる。
- 作る時間（手元の Node、ステージ 1〜120）: 平均 84ms、最悪 0.32 秒。条件に合うまでシードを変えるぶん M6 の1盤面より長い。机は板が少なくねじが 21 本を超えにくいので、机のねじの下限は 18 本で止めた（止めないと 40 シード全部を試して 2 秒かかっていた）。
- 到達ステージは `src/progress.js` の `createProgress(storage)`（localStorage を外から渡す。テストは Map で代用）。キーは `screw-puzzle-3d.stage`、クリアした瞬間に次の番号を書く。前のステージを遊び直しても到達は戻らない。読み書きで例外が出ても遊べる。
- 画面: 既定はステージの進行。`?stage=番号` でそのステージ（見るだけでは到達は進まない）、`?seed=番号&kind=種類` は生成盤面を1つだけ（保存しない）、`?level=box` は M3 の固定の箱（M4・M5 のスクリーンショットはこれを使う）。クリアの画面に「次のステージへ」、ステージが変わると立体の向きと距離を最初に戻す。`window.__app` に `stage`・`level`（盤面の meta）・`why()`（rendered が false の理由）を足した。
- スクリーンショットは `SHOTS=box,gen,stage` で組を絞れる。stage の組は保存の無い新しい端末として開き、ステージ 1〜3 を順にクリアして「次へ」をタップで進め、再読み込みでステージ 4 から始まることを確かめる。
- 見つけた問題（M8 で直す）: 生成した箱（シード 4）を手順どおりに解くと、底板の下に付いた札がぶら下がったまま、外れた底板がその上に載って触れ合い続け、物理がいつまでも落ち着かないことがある（フレームの間隔しだいで起きたり起きなかったりする）。ねじの軸は盤面に固定されているとみなしているので、外れた板の上にぶら下がる札が残る。スクリーンショットのスクリプトは、板が動き続けるだけなら 15 秒で先へ進む（警告を出す）。画面では描画と物理が止まらず電池を使い続けるので、落ち着きの判定か、宙に浮いた札の扱いを M8 で詰める。
- テストは生成器とステージで多数の盤面を作るので、並列に走ると既定の 5 秒で打ち切られた。`vite.config.js` の `test.testTimeout` を 30 秒にした（速さの検査はテストの中で時間を測っていて、そちらは緩めていない）。

### M8 で分かったこと

- JS は約 5MB → 0.8MB（gzip 0.2MB）。物理の wasm（3.1MB、gzip 1.2MB）は `dist/assets/rapier-*.wasm` に分かれた。やり方は `vite.config.js` のプラグインで、Rapier の互換版に埋め込まれた base64 をビルドのときだけ `.wasm` に取り出し、init に URL を渡す（`.buffer` まで含めて置き換える。最初は `.buffer` を残して URL の .buffer を渡し、init が既定の URL を探しに行って落ちた）。開発サーバーと Node のテストは埋め込みのまま。サーバーが `application/wasm` で返さなくても（Capacitor など）、wasm-bindgen が警告を出して読み直すので動く（手元で確かめた）。
- 止まらない物理の正体は、M7 の札と板に限らず「隣の板に押し付けられて接触が震え続ける」「隣の板の間で数度の幅で揺れ続ける」ぶら下がりの板だった。ステージ 1〜30 の手順を、1本ごとに重力を8方向へ向け直して数えると、速さだけの判定では 20 秒たっても止まらない場面が十数か所あった。`physics.js` に、姿勢からほとんど離れないまま一定時間たったら落ち着いたとみなす判定（`STILL`）と、最後の変化から 1200 刻みで止める歯止め（`RESTLESS_STEPS`）を足し、歯止めに頼らず全部止まるようになった（`test/physics.test.js` の「板の動きはいつか落ち着く」）。スクリーンショットのスクリプトは、落ち着かなければ警告ではなく失敗にした。
- 宙に浮いた札（外れた板に付いていた札が、ねじの位置にぶら下がったまま残る）は直していない。ねじは盤面に固定とみなす約束（M5）のとおりで、払い落とせば消える。気になるなら、板が外れたときにその板に載った札も外す形がありうる（ルールの変更になる）。
- 描画: 何かが変わったときだけ描き、止まっていればフレームの呼び出しも止める（`main.js` の `requestRender` / `wake`）。何かを動かすときは `requestRender()` か `tween()` を呼べば、フレームが回り出す。DPR 2 以上ではアンチエイリアスを切り、動かしている間の平均が 24ms を超えたら描く解像度を下げる。中級機の実機では確かめていない（ヘッドレスの Chromium だけ）。重いと感じたら `SLOW_FRAME_MS` と `PIXEL_RATIOS` を見直す。
- 操作: ねじを選ぶ半径は 32px（`pick.js`）、回る速さは画面の短い辺で半回転（`view.js` の `radPerPx`）。右下に「向きを戻す」と「音と振動」のボタン（48px）。
- 効果音と振動は `src/feedback.js`。合図の名前（unscrew / blocked / full / box / slot / boxFull / plate / cleared / stuck）ごとに振動の型と音の型の表がある。音は Web Audio の合成で、最初のタッチで鳴らせるようになる。設定のキーは `screw-puzzle-3d.sound`。
- スクリーンショットの `SHOTS=size` は、小さめ 360×640・普通 390×844・大きめ 430×932 で、ステージ 7 と生成した箱の途中・クリアを撮り、HUD とボタンとねじが画面に収まっているか、中心から 26px ずれたタップで外れるか、「向きを戻す」で戻るか、音の設定が再読み込みで残るかを確かめる。CDP のタッチでドラッグした直後に間を空けずにボタンをタップすると、Chrome が click にしない（人の指ではありえない速さなので、スクリプトで 0.3 秒空けている）。

### D1 で分かったこと

- 見た目の値は `src/theme.js` の `THEME` にまとまっている（ねじの色・板の色の並び・札の色・材質・光・映り込みの景色・空とマットと影の色・HUD の色）。色を変えるときはここだけ触る。HUD の CSS 変数は `cssVariables()` を `main.js` が起動時に入れる。
- 立体の形は `src/scene.js`。板は `roundedShape`（凸多角形の角を丸める）で輪郭を作り、面取りの幅だけ縮めてから押し出す。キャップボルトの比は `BOLT` の表。`test/theme.test.js` が、描く回数（板1回・ねじ3回）、形と材質の使い回し、板の外形が当たりの形と同じ大きさ、頭が当たりの半径に収まり札の厚みより低い、ねじ部が板を突き抜けない、六角穴を当てても id が分かる、を見張る。
- 背景（空・マット・影）は CSS の `body` の背景。マットと影の位置は画面の高さの割合で決めていて、立体の位置（HUD の高さの分だけ下寄り）とは連動しない。ズームしたり、題材で立体の大きさが変わったりして浮いて見えるなら、`main.js` から影の位置と大きさを CSS 変数で渡す形にする。
- 影の地図を使わないので、板が重なった所の暗さは出ない。D2 以降で物足りなければ、まず影を受けるのはマットだけ（CSS の影の楕円を立体の向きに合わせて動かす）にして、3D の影は最後の手段にする。
- `test/generator.test.js` の「生成はスマホで待てる時間で終わる」は、ブラウザのスクリーンショットを同時に走らせて CPU が混むと最悪 1 秒を超えて落ちることがある（単独では通る）。手元で並べて走らせない。

### D2 で分かったこと

- 演出の時間と動きの曲線は `src/effects.js`（`FX` の表と `unscrewPose` / `burstPose` / `dropPose` / `flyFrames` / `boxCloseTimeline` / `groundOf`）。DOM にも three.js にも依存しないので `test/effects.test.js` で確かめている。`main.js` はこの曲線で立体と HUD を動かすだけ。
- ねじは右ねじとして、頭から見て反時計回りに、1回転でピッチ1つ分（`scene.js` のらせんの間隔）だけ抜ける。ねじ部が抜けきるまで約 3 回転し、抜けた後はポンと飛び出して少し膨らみ、画面の印（DOM）に持ち替えて回りながら飛ぶ。持ち替えた所に、ねじの色の輪が広がる。
- 板の「はじけ」は、最後のねじを外した瞬間に、その板の Mesh の大きさを 7% 膨らませ、材質の自己発光で白く光らせるだけ。物理の形や力は変えていない（ルールと物理のテストはそのまま）。板ごとに材質が1つなので、光らせても描く回数は増えない。白い板では光がほとんど見えず、膨らみだけが目立つ。
- 箱のふた・印の着地のはずみ・ポンの輪・星は全部 CSS（`style.css`）。3D の描く回数は増えない。`test/effects.test.js` が全ステージ（1〜30）の描く回数（板1・ねじ3）と三角形の数（8 万枚まで。ステージ 7 で約 5 万、ねじ1本 1866 枚のうち頭のローレットが 1512 枚）を見張る。重ければ、まず `BOLT.knurls` かローレットの刻み（`steps = N * 4`）を減らす。
- 箱が満杯になったときの音と振動（`boxFull`）は、ふたが閉まりきる瞬間に鳴らすようにした（以前は箱が消えた後）。1回のタップの演出は、箱を満杯にする1本でも 1.4 秒以内、解く手順の平均は 1 本 1 秒以内をテストで守る。
- D1 の申し送りのマットと影は、立体を包む球の見かけの大きさと立体の中心の画面の位置から決めるようにした（`groundOf`、CSS 変数 `--mat-*` / `--shade-*`）。寄り引き・画面の大きさ・盤面の大きさに付いてくる。回したときは動かさない（球は回しても同じで、背景を毎フレーム描き直さない）。係数は固定の箱を最初の距離で見たときに D1 と同じ見た目になる値。
- 演出の時計（`fxClock`）は、スクリーンショットのスクリプトが `__app.timeScale(k)` で遅くしたり止めたりできる（CSS のアニメーションも止まる）。ヘッドレスの Chromium はソフトウェアの GL で1フレームが重く、実時間のまま `waitForTimeout` で撮ると演出の途中を撮り逃がす。`SHOTS=fx` は生成した箱（シード 4）を手順どおりに外しながら、抜ける途中・はじけ・箱のふた・落ちる板を撮り、演出の後に立体の Mesh が増えていないことを確かめる。
- 実機のスマホではまだ見ていない（ヘッドレスの Chromium だけ）。重かったら `FX` の時間を短くするより先に、ねじのポリゴンを減らす。

### D3 で分かったこと

- ネジまるは `src/mascot.js`（形と描き手）と `src/mascot-motion.js`（どの合図でどう動くか・姿勢の曲線。DOM にも three.js にも依存しない）。`main.js` は `cue(name)` で音と振動とマスコットに同じ合図を配り、終わりの画面ではキャンバスをカードの中へ移す（`seatMascot`）。色は `THEME.mascot`。
- 形は試作をそのまま組んでから `bake()` で「動かす部分（`userData.part`）ごと・材質ごと」に1つへまとめる。部分の名前（`head`・`arm-1`・`eyesOpen` など）に `applyPose()` が姿勢を当てる。部品を足すときは、動かすなら `part()` で包み、動かさないなら親の部分の下に置くだけで描く回数は増えない。
- `test/mascot.test.js` が、合図と動きの対応、成功と失敗がやり直すまで続くこと、描く回数（どの姿勢でも 24 回まで、今は姿勢により 19〜24）と三角形（2 万枚まで、今は約 1.4 万）、どの動きでも左下（108×140）とカード（150×194）のキャンバスからはみ出さないこと（頂点を全部カメラへ写して確かめる）を見張る。キャンバスの大きさや `FRAME` を変えたらここが落ちる。
- 盤面の描き手と別なので、WebGL の文脈が2つになる。映り込みの PMREM も描き手ごとに1回焼く（`src/env.js`）。古い端末で文脈の数が問題になったら、マスコットを盤面の描き手の `setScissor` で描く形に寄せる（その場合、待機の動きのために盤面も描き直すことになる）。
- スクリーンショットは `SHOTS=mascot`（姿勢を並べた `mascot-poses.png`、クリアと詰みのカード）。`__app.mascot.force(動き, 秒)` で姿勢を決め打ちでき、`__app.mascot.history` で合図が届いたかを確かめられる。詰みの局面は作らず、カードの文字と姿勢だけ替えて撮っている（詰みへの配線はクリアと同じ `showEnd` → `cue(endCue())`）。
- 実機のスマホではまだ見ていない。重ければ、待機の描く間隔を広げる（`createMascot` の `frameNo % 2`）か、球の分割数を減らす。

### クリアの評価で分かったこと

- 評価は `src/rating.js`（`rate` / `parSeconds` / `better` / `clock` / `createPlayClock` / `createBests`）。DOM に依存しないので `test/rating.test.js` で星の決まり・時計の止め方・自己ベストの残し方と壊れた値の扱いを確かめている。
- 星は ★3 − ヒントの回数 − 戻るの回数 − （時間が目安を超えたら 1）、最低 ★1。目安はねじの本数 × 6 秒。
- ヒントと戻るの回数は `main.js` の `countHint()` / `countRewind()` で数える（`window.__app` にも出してある）。ヒントと戻るのスレッドは、使った瞬間にこれを呼べば評価に入る。ヒントは電球を押して輪が出たときに呼ぶ（手順が見つからなかったときは数えない）。戻るはまだ呼ばれていない。「やり直す」「もう一度」で 0 に戻る。
- 時計（`playClock`）は `restart()` で 0 から動き出し、クリアか詰みを決めた `tapScrew` で止まり、`visibilitychange` で裏に回っている間も止まる。終わりの画面の時間は演出を待つ時間を含まない。
- 終わりのカードに星3つ（付いた星は 0.18 秒ずつずらしてはじける、CSS）と、時間（目安）、ヒント・戻るを使ったときはその回数、自己ベスト（初めてのクリアでは出さない。更新したら「自己ベスト更新！」、しなければ前のベスト）を出す。詰みのカードには出さない。`.card #end-score` の display を上書きしたので、`[hidden]` も `.card` 付きで書かないと詰みでも出てしまった。
- スクリーンショットは `SHOTS=rating`。保存の無い端末でステージ 1 を2回クリアし（2回目はヒント1回の扱い）、星が決まりどおりか、自己ベストが出るか、再読み込みで残るかを確かめる。
- 2D 版のネジまるは ★3・★2・★1 で喜び方を変えていたが、3D のネジまるはどの星でも同じバンザイのまま。変えるなら `mascot-motion.js` に動きを足して、`showEnd` の `cue` を星で分ける。

### ヒントで分かったこと

- ヒントは `findHint(level, state, isBlocked)`（`src/hint.js`）。生成器と同じ `solve` に `from`（途中の局面）を渡せるようにし、隠れ判定は安全側の見積もり `safeBlocker`。返す手順は「板を外したら傾けて落とし切る」遊び方で実際にも外せる。1局の側は `game.hint(prefer)` で、使った回数 `game.hints` も数える（やり直しで 0）。画面の側は輪を出したときに評価の `countHint()` を呼ぶ。
- 探索がそのまま返す最初の手は裏側のねじのことが多いので、今画面で見えているねじ（`visibleScrews()`）を `prefer` に渡し、その中から最初の手にして解けるものがあればそちらを指す（8 本まで試す）。
- 画面は右下の電球ボタン。最初に外すねじに金色の輪を5秒出す（2D 版と同じ）。輪はねじの子で、奥行きを無視して手前に描くので、板の向こう側のねじでも場所が透けて分かる。ねじが向こう向きなら「回して探そう」、落ちた板やぶら下がった板に今隠れているなら「先に払い落とそう」と添える。
- 探す速さ（手元の Node、ステージ 1〜20 と生成シード 21〜60 をでたらめに外した途中の約 700 局面）: 平均 4ms、最悪 0.13 秒。打ち切り（2 万局面）は一度も起きなかった。
- でたらめに外した途中の局面の約 3 割は、安全側の見積もりでは解ける手順が無い（待機スロットの使いすぎや、閉じ込められる板を作る手）。そのときは「解ける手順が見つからない。やり直そう」と出す。見積もりは物理より厳しいので、実際にはまだ解けることもある。「戻る」ができたら、そちらへ案内するとよい。

### 戻るで分かったこと

- 戻すのは「ルールの状態」と「物理の写し」の組。ルールは `createGame` が外した手ごとに外す直前の状態を覚え（`history`。状態は書き換えない作りなので、そのまま持てる）、`undo()` / `rewind(k)` で戻す。物理は `physics.snapshot()` / `restore()`。Rapier の `takeSnapshot` / `World.restoreSnapshot` で世界を丸ごと（速さ・軸・接触まで）写し、板の状態と落ち着きの数えは `physics.js` の側で写す。手の履歴から再生する案は、重力の向き（立体を回した向き）を刻みごとに覚える必要があり、戻すたびに何百刻みも計算し直すのでやめた。
- 写しから戻して同じ操作をすると、写さずに続けたときと浮動小数まで同じ姿勢になる（`test/physics.test.js` の「写した所へ戻して同じ操作をすれば…」。ステージ 7 の手順で、落ちきって消えた板が戻ることも含めて確かめた）。写しは外す手ごとに1つ（板 10 枚ほどで数十 KB）。
- 戻した後の画面は、盤面を作り直してから、外したねじを隠し、消えた板を外し、動ける板を写しの姿勢に置く（`main.js` の `rebuildBoard` / `showState`。やり直しも同じ道を通る）。揺れていた板は揺れの途中から続く。
- 「解ける所まで戻る」は 2D 版と同じ考え方（`game.js` の `rewindPoint`）。最初の局面は解ける、今の局面は解けないとみなし、その間を二分法で `solve(level, safeBlocker, { from })` を呼んで詰める。ステージ 1〜30 をでたらめに詰ませた 88 局で、平均 22ms・最悪 0.13 秒（手元の Node）。見積もりは安全側なので、戻る先は本当の分かれ目より手前になることがある。分かれ目のねじ（戻った局面で外したために解けなくなったねじ）には、ヒントと同じ輪を赤で 4 秒出す。
- 3D のこのゲームでは、詰み（待機スロットが満杯で、出ている箱の色のねじが全部、動かない板に隠れている）はめったに起きない。ステージ 1〜7・9〜13・15・20・30 で、待機スロットへ入れる手を優先して 300 局ずつでたらめに外しても1回も詰まなかった（ステージ 25 では 9 手で詰む順が見つかった。スクリーンショットはこれを使う）。代わりに起きるのは「詰みではないが、解ける手順がもう無い」局面なので、ヒントで手順が見つからないときに「行き止まり」の画面を出し、そこから「解ける所まで戻る」「1手戻す」「このまま続ける」を選べるようにした。
- 右下の「1手戻す」（↶）は、外した手があって終わりの画面が出ていない間いつでも押せる。何回でも戻せる。クリアの後は戻せない。戻すたびに（1手でも解ける所まででも）クリアの評価の「戻る」を1回数える（★が1つ減る）。音と振動の合図は `undo`。
- スクリーンショットの `SHOTS=undo` は、生成した箱で2手戻して外し直すと同じ局面になること、ステージ 25 で行き止まりの画面、詰みの画面の「1手戻す」、「解ける所まで戻る」と赤い輪、そこからヒントでクリアして評価に「戻る 2 回」が出ることを確かめる。

### D4 で分かったこと

- 部品の木は `src/parts.js`。節は `{ id, shape, size|outline|radius, thickness, at, n, u, faces, role, color, children }` で、`at`・`n`・`u` は親の局所の軸（u, v = n × u, n）で書く。`flattenTree` が親から順に盤面の板へ直し、板に `parent`・`role`・`color` を足す。盤面からは `partTree(level)`（根と子の表）と `depthOf` でたどれる。家具（箱・本棚・机）の板は parent を持たず、それぞれが根。
- 部品の形は `board.js` の `shape`: 'plate'（今までの板）・'block'（丸めた箱。当たりは直方体のまま、見た目だけ丸める）・'cylinder'（円柱。当たりは円に外接する 12 角形の柱、見た目の円柱がはみ出さない側）。どれも「凸の輪郭を局所の z へ押し出した柱」なので、`outlineOf` を足しただけで隠れ判定（GJK）・安全側の見積もり・物理（凸包）がそのまま動いた。三角の屋根は outline が三角の板。ねじは今までどおり局所の z の面（faces）にだけ置く。斜めの屋根板のねじ（軸に沿わない向き）も問題なく扱える。
- 題材は `src/themes.js`（車 car・家 house・ぶた animal）。生成器は `kind` に題材を渡すと木から組み、部品ごとに局所の xy でねじを置く（`placeOnPart`。狭い部品は乱数で2本目が入りにくいので、一番離れた2点に置き直す）。全体の外接箱の中心を原点へ動かす。札は載せない（窓・ドア・ぶちなどの飾りの部品が札の代わり）。`kind` を省いたときは今までどおり家具だけから選ぶ（`KINDS`。M6 からのシードの盤面は変わらない）。題材込みの一覧は `ALL_KINDS`。
- ステージは 7 から先を `ROTATION`（箱・車・本棚・家・机・ぶた）で回す。8 が最初の車。ステージ 1〜7 は変わらないが、8 から先の盤面は D3 までと変わった（到達したステージ番号は保存のまま使える）。ねじの下限の頭打ちは机 18・家 21（`SCREW_CAP`）。
- 部品が増えるほど、色の割り当てが解けないことが増えて作るのが遅くなる（ぶたは最初 14 枚で平均 0.36 秒、最後の砦 9/60）。ぶちを左右 1 枚まで・しっぽを 6 割にして 12 枚までに抑え、`safe.js` の抜け出す道の判定に「ぶら下がった板の弧全体の外接箱」での先の弾きと、覚えておく表の引き方の改善を入れた（結果は同じ。家具の盤面にも効くが、測ってはいない）。手元の Node で、題材 1 盤面の平均は車 0.05・家 0.05・ぶた 0.13 秒、最悪 0.5 秒。ステージ 31〜60 は平均 0.14 秒・最悪 0.5 秒。
- 隠れ判定と物理の突き合わせ（`test/safe-physics.test.js`）は題材も回す（CI は各 6 シード、手元で各 40 シード、見積もりが甘い場面は 0）。初め、家の庭（土台）を壁より前に張り出していたら、ぶら下がったドアの振れる範囲が庭にかかって、どの向きにも抜け出せない扱いになり、全シードで解けなかった。土台は壁の前後と面一にした。題材を作るときは「外側の部品の振れる範囲の下に、張り出した部品を置かない」。
- 部品どうしは触れてよいが重ならない、子は親に触れている、根は1つ、を `test/parts.test.js` が全題材 30 シードで見張る。かぶさる部品は厚み 0.3 以上（板から出るねじ頭 0.27 が中に隠れるように）。
- ルールは変えていないので、親の板を先に外すと子の部品は宙に残る（家具の札と同じ。ねじは盤面に固定）。手順どおりに外すと、車体が先に消えて客室と車輪が浮く場面がある（`theme-car-midway.png`）。D5 で層を数えるときに、親のねじを子で隠す置き方に寄せるか、子を親と一緒に外すルールにするかを決める。
- スクリーンショットは `SHOTS=theme`（各題材を開いた直後と下から見た向き、車を途中まで外したところとクリア）。

### D5 で分かったこと

- 親子の扱いはルールで決めた（`rules.js`）: 子の板が残っている間、親の板の最後のねじは外せない（理由 `'held'`）。ねじが 2 本以上残るうちは外せる。隠れているかより先に調べる（安くて、探索が速くなる）。`checkRemove` を通る所（ゲーム・探索・ヒント・戻る・詰みの判定）は全部そのまま従う。画面ではねじが震え、留めている子の部品が橙色に 2 回染まり、「付いている部品を先に外そう」と出る（`game.tap` が `holders` を返す）。明るい板は emissive だけでは白く飛ぶので、色そのものを寄せている。家具の札も載っている板の子にした（`parent`）。
- このルールを入れた直後、車の盤面が作れなくなった（シード 10 個で形の作り直し 85 回）。探索が最初に車体をぶら下げ、車体は子を外し終えるまで落とせないので、長くぶら下がったまま周りを隠し続けて行き詰まっていた。`solve` の手の順に「子が残っている板をぶら下げる手は一番後」を足して直った（車の平均 0.66 → 0.05 秒）。
- 層は `layers.js` の `plateLayers`。始めの局面から、ほかの板に手を付けずに外し切れる板を層 0、それを全部外した局面で外し切れる板を層 1 … と数える（1 色の盤面として、安全側の見積もりとルールで）。題材は親子の決まりで木の深さがそのまま層になり、車 3〜4・家 4・ぶた 3 段。家具は 1〜4 段（机は 1〜2 段が多い）。
- ねじの置き方は `generator.js` の `LAYER_TABLE`（役ごとに本数の下限と、子の下に隠す本数）。芯は 3 本以上で 2 本を子の下、骨組みは 1 本を子の下。子の頂点を親の局所へ写した凸包をねじ頭の半径だけ縮め、その中の格子点から選ぶ（GJK を使わず安い）。子が親の面に載っていない部品（家の三角の屋根、ぶたの脚の上の胴）には置けない。芯と骨組みのねじは D4 でも半分以上が偶然子の下にあったが、これでほぼ全部になった。
- 難しさは `meta.difficulty`（`{ layers, perLayer, slots }`）。`slots` は見つけた手順で待機スロットへ置いた回数で、最短ではない（探索は箱へ入れる手を先に試すので、0 なら「待機スロットなしで解ける」）。生成器の `minSlots` は、解ける色の割り当てが見つかってから 3 回まで割り当てを変えて満たすものを探す。ステージは 7 から層 2 段以上を条件に、待機スロットは 25 から 1 回・37 から 2 回を「なるべく」（3 シードで見つからなければ外す）。ぶたは手順に待機スロットが要らない割り当てになりやすく、必ずにすると作るのが 1〜2.6 秒かかった。ステージ 25〜48 で待機スロットの条件を満たしたのは 6 割以上（テストで見張る）。
- 生成器の色の割り当ての探索で、安全側の見積もりを 1 色の盤面のものに使い回すようにした（見積もりは形だけで決まる）。割り当てごとに作り直していたぶん速くなった（手元の Node、シード 1〜20 の平均: D4 の master でぶた 0.11・家 0.05 秒 → 0.06・0.03 秒。車は親子の決まりで形の作り直しが増え、0.04 秒のまま）。
- ねじの数に上限（下限 + 6 本）を足した。層の条件で机の 1 段の盤面を弾くと、早いステージ（7〜12）のねじが後（25〜30）より多くなり、「進むほど難しくなる」のテストが落ちたため。ステージ 31〜60 を作る時間は手元の Node で平均 0.16 秒・最悪 0.45 秒。
- ステージ 2 から先の盤面は、札の親子と色の探索の変化で D4 までと変わる（形は同じで、色と手順が変わるものが多い）。ステージ 1 は札が無いので変わらない。到達したステージ番号は保存のまま使える。
- 隠れ判定と物理の突き合わせは、題材 40 シードずつ手元で回して見積もりが甘い場面は 0（CI は 6 シードずつのまま）。
- スクリーンショットは `SHOTS=theme` に `theme-car-held`（片側の窓を外して客室を 1 本にし、もう片側の窓が付いたまま最後のねじをタップしたところ）を足した。`theme-car-midway` は、D4 では車体が先に消えて客室と車輪が浮いていたのが、車輪から外れて車体が残る形になった。

### D6 で分かったこと

- ランダムは `src/random.js`。「おまかせ」は番号（1〜999999）と難しさ（easy・normal・hard）で、「今日の1問」は端末の日付（`20261003` の形の数）で盤面が決まる。どちらも `stageConfig` の帯（やさしい 7〜12・ふつう 19〜24・むずかしい 37〜42）の設定を借り、形は番号の乱数で 6 種から選んで、その形の帯の中のステージの設定で作る。盤面の選び方はステージと同じ関数（`stages.js` の `pickLevel`。`stageLevel` もこれを使うように分けただけで、ステージの盤面は変わらない）。生成器のシードは、おまかせが 1 億 + 番号 × 50 + 試した回数、今日の1問は番号 100 万 + 2000-01-01 からの日数のおまかせ（ふつう）として作る。ステージ（n × 1000 + 試した回数）とは重ならない。
- 解ける保証と親子のルールは、生成器が手順を見つけた盤面しか返さないことと、ステージと同じ条件で選ぶことで守る。`test/random.test.js` が、3 段 × 8 番号と今日の1問 4 日ぶんで、手順を安全側の見積もりと本当の隠れ判定の両方で打ってクリアになること、手順の中で親の最後のねじを外す手の前に子が残っていないこと、借りた設定がステージの帯と同じこと、形が偏りすぎないこと（1200 番号で各形 120 以上）、難しくするほど待機スロットを使う回数が増えることを見張る。
- 手元の Node で番号 1〜30: やさしい平均 0.06 秒（最悪 0.29）、ふつう 0.10 秒（0.38）、むずかしい 0.20 秒（0.65）。ねじは 18〜27 本で、3 段ともあまり変わらない（ねじの数の下限は形ごとの頭打ち 18〜24 本に早く届くため）。違いは色（4・5・6 色）と札の数、手順で待機スロットを使う回数（平均 0.6・2.3・4.0 回）に出る。ねじの数でも差をつけたいなら、形ごとの頭打ちを上げる必要がある。
- 画面: 題名が「遊び方」の画面を開くボタンになった（▾ 付き）。ステージ（続きから）・今日の1問（日付と、クリア済みなら星と時間）・おまかせ 3 段。おまかせの題名は「おまかせ・むずかしい」で、下に「#番号」。クリアの画面の「次へ」は、おまかせなら「次のおまかせ」（同じ難しさの新しい番号）、今日の1問なら「ステージの続きへ」。おまかせ・今日の1問はステージの到達を進めない。自己ベストは今日の1問だけ `daily-20261003` の名前で覚える（ステージのベストと同じ保存先）。遊び方の画面を開いている間は時計を止める。
- `?random=番号&diff=easy|normal|hard` でおまかせのその番号、`?daily=20261003`（`?daily` だけなら今日）で今日の1問を開ける。
- 今日の1問の日付は端末の時計（地域の日付）で決まるので、時差のある端末どうしでは日付の変わり目がずれる。再読み込みするとステージに戻る（おまかせを続けていたことは覚えない）。（E10 で片づけた: 再読み込みでも遊び方と局面が続く）
- スクリーンショットは `SHOTS=random`（遊び方の画面、おまかせのむずかしいを開いた直後・クリア・次の1問、今日の1問を開いた直後・クリア、クリア済みの遊び方の画面）。

### 設定で分かったこと

- 設定は `src/settings.js`（`createSettings(storage)`）。音・振動・回す速さ（ゆっくり 0.7・ふつう 1・はやい 1.4 倍）・画質（自動・軽い）・ネジまる（出す・隠す）を localStorage `screw-puzzle-3d.settings` に JSON で1つにまとめて持つ。知らない値や壊れた保存は項目ごとに既定へ戻す。M8 の `screw-puzzle-3d.sound` が `off` の端末は、新しい保存が無いうちは音も振動も切ったまま始まる（前は1つのボタンで両方を切っていたため）。`onChange` で変わった項目だけを画面に効かせる（`main.js` の `applySetting`）。
- `feedback.js` は保存をやめ、鳴らすたびに設定の `sound` / `vibrate` を読む。右下の音のボタンは音だけを入り切りする（振動は設定の画面で）。
- 画質「軽い」: 盤面の解像度を 1 に固定（自動は 2 → 1.5 → 1.25 → 1 と重いときだけ下げる）、ねじの頭のローレットを刻まない（`buildBoard(level, { knurl: false })`、遊んでいる途中は `setKnurl(board, false)` で頭の形だけ差し替える）、ネジまるも解像度 1 で待機中は 4 フレームに 1 回描く。三角形はステージ 7 で 40838 → 16646、ステージ 20 で 49492 → 21844（ねじの頭が大半）。DPR 2 の画面では縁のアンチエイリアスも切ったままなので、縁が少しギザギザになる。
- ネジまるを隠すと、キャンバスを `body.no-mascot` で消し、描く繰り返しも止める（合図は受けたまま。出し直すと今の動きから続く）。
- 記録を消すは、到達したステージと自己ベスト（今日の1問を含む）だけを消し、設定は残す。1回目の押しで「もう一度押すと消えます」に変わり、4 秒以内にもう一度押すと消して、クエリを外したページを開き直す（ステージ 1 から）。
- スクリーンショットは `SHOTS=settings`（設定の画面、画質「軽い」とネジまるを隠した盤面、記録を消すの確かめ）。同じ 120px のなぞりで「はやい」が「ふつう」の 1.4 倍（±0.15）回ること、解像度が 1 になること、再読み込みで残ること、記録を消すとステージ 1 に戻り設定は残ることも確かめる。
- 実機ではまだ確かめていない。重い端末で「軽い」でも足りなければ、次はねじ部（らせんの管）の分割を減らすか、映り込み（PMREM）を切る項目を足す。

### E10 で分かったこと

- 保存は `src/resume.js`（DOM 無し）。localStorage の `screw-puzzle-3d.resume` に1つだけ、`{ v, mode, stage, sig, path, seconds, hints, rewinds, view: { q, d }, physics, at }` を置く。既存のキー（到達したステージ・自己ベスト・設定）の形は変えていない。「記録を消す」はこれも消す。`test/progress.test.js` が、ステージ・おまかせ・今日の1問それぞれで保存→開き直し→同じ局面と履歴、古い端末の記録が1文字も変わらないこと、壊れた保存・指紋違い・クリア済みを捨てることを守る。
- ルールの局面は `replayPath(level, path)` で頭から打ち直す（隠れ判定はしない。その時の物理で外せたことは確かめてある）。戻るの履歴（各手の直前の局面）も同じ打ち直しで作れるので、続きから戻した後も「1手戻す」「解ける所まで戻る」は保存前の手まで届く。
- 物理の写しは 20〜45KB（base64）。手ごとに `physics.snapshot()` を JSON にしても、ヘッドレスで外す手の間隔に目立つ遅れは無かった。写しを JSON に通して戻しても、そこからの続きは写さずに続けたときと浮動小数まで同じ（テスト）。保存より前の手へ戻すときは `settle()`（ルールの状態から物理を作り直して落ち着くまで進める）。
- 板が落ち着いた瞬間にも保存するのは、手の直後の写しだと板がまだ落ちている途中で、再読み込みすると落ちる途中から続いてしまうため（それでも正しいが、裏へ回る時の保存が間に合わない端末のために）。
- スクリーンショットの `SHOTS=resume` は、ステージ 8・おまかせ・今日の1問を途中まで外して再読み込みし、遊び方・題名・外した順・箱とスロット・板の状態と姿勢（1e-4 まで）・向き・遊んだ時間が続くこと、続きからクリアすると保存が消えて次のステージになること、保存前の手へ2手戻せること、指紋の合わない保存は黙って最初から始まることを確かめる。

### E1 で分かったこと

- カメラの距離は盤面ごとに `frameBoard()`（`main.js`）が決める。空きは `fitRegion()`（HUD の下端 +6 からボタン列の上端 −6、左右 12px の余白。小さい画面でボタン列が高いときは横幅の 0.95 倍まで下へ延ばす）、距離は `fitPoints()`（最初の向きの頂点を空きの 82% に収める閉じた式）と `fitDistance()`（包む球が空きの短い辺の 1.35 倍を超えない下限）の大きい方。どれも `view.js` にあり three.js に依存しない。立体の中心（原点）は `setViewOffset` で空きの真ん中に描く。
- 寄り引きは「収めた距離に対する比」`zoomK`（0.62〜1.8）で持つ。盤面が変わると 1 に戻し、画面の大きさが変わっても比は保つ。「向きを戻す」は向きと一緒に 1 へ戻す。スクリーンショットの `__app.view(x, y, z, k)` の 4 つ目も距離ではなくこの比になった（19 → 1、17 → 0.9、27 → 1.42 に書き換えた）。
- 390×844 で立体が空きに占める割合（幅と高さのきつい方）: ステージ 1 80%、8（車）80%、10（家）77%、12（ぶた）79%、37 79%。E2・E8・E9 を取り込んだ後（12 はロボット、37 は別の盤面になった）は、1 80%、8 79%、10 77%、12 82%、37 81%。360×640・430×932 のステージ 8 も 80%。`SHOTS=frame` が 70〜95% の外なら失敗にする。`__app.boardRect()` で立体の外接の四角、`__app.framing` で空きと距離が読める。
- マットと影は、包む球ではなく最初の向きの立体の広がり（`groundRadius`）から置く。球のままだと家のように球が立体より大きい形でマットが下へ離れ、立体が浮いて見えた。
- 慣性は `createInertia()`（`view.js`）。`main.js` は指の出来事の時刻で `push`、全部の指が離れたら `release`、`frame()` で `step` して `rotateBy` に渡すだけ。止まっていない間は `__app.rendered` が false なので、スクリーンショットのスクリプトは惰性が止まるまで待つ。
- ヘッドレスの Chromium は描画が遅く、CDP で送る指の動きの間が 200 ミリ秒ほど空く（止めてから離したことになり惰性が付かない）。惰性を確かめる所だけ、ページの中で `PointerEvent` を 12 ミリ秒おきに合成して送る。合成した指は `setPointerCapture` できないので、`main.js` で例外を握りつぶしている。スクリプトの `drag()` は既定で、なぞり終えてから 150 ミリ秒止めてから離す（惰性を付けない。回す速さの 1.4 倍の検査が揺れないように）。
- 案内の行 `#hint` は HUD の外（`position: absolute`）の札になり、空のときは透明。HUD の高さが文で変わらないので、立体の距離も変わらない。
